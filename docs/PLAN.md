## 1. Зафиксированные решения

| Вопрос             | Решение                                                                                       |
| ------------------ | --------------------------------------------------------------------------------------------- |
| Стек               | Node.js 24, TypeScript (ESM, `strict`), чистая архитектура                                    |
| MCP                | `@modelcontextprotocol/server@^2.3.1` + `mcp-handler@^2.3.0`                                  |
| Транспорт          | **только HTTP** через `mcp-handler` (`createMcpRouteHandler`), один сервер                    |
| БД                 | `node:sqlite` (players, api_keys, state JSON, events, snapshots)                              |
| Игроки             | MVP — один локальный игрок; модель данных **player-scoped с первого дня**                     |
| Мультиплеер        | в roadmap: фаза R1 — мультиплеер по API-ключу, R2 — авторизация поверх (см. §11)              |
| LLM                | нет встроенного раннера: играет внешний MCP-клиент                                            |
| Generative UI      | **убран из MVP**, перенесён в «после MVP» (см. §10)                                           |
| Стратегия контента | **B**: структура слоёв — по MIT-Antimatter Dimensions, числовые кривые — ориентир Melvor-вики |
| Дебаг-страница     | статическая (написанная руками) HTML-страница состояния игры, тот же HTTP-сервер              |

Зависимости MVP: `@modelcontextprotocol/server`, `mcp-handler`, `zod@^4`,
`neverthrow@^8.2` (Result/Ok/Err в домене и application). Dev: `typescript`,
`@types/node`.

TypeScript: dev — нативный strip-types (`node --watch src/bootstrap/server.ts`,
только erasable-синтаксис: без `enum`, без parameter properties), prod — `tsc` →
`dist` → `node dist/bootstrap/server.js`.

## 2. Игра: что делает игрок

Игрок — LLM-агент (или человек), подключённый как MCP-клиент. Он поддерживает
idle-цикл: ставит активное действие, оно тикает в реальном времени, приносит
ресурсы и опыт; агент продаёт добытое, покупает апгрейды, качает скиллы, бьёт
монстров, выполняет квесты, в конце концов делает престиж. Наблюдатель смотрит
на ту же игру через дебаг-страницу.

### 2.1 Скиллы (8)

| Скилл    | Что делает          | Продукты                           |
| -------- | ------------------- | ---------------------------------- |
| Рубка    | деревья             | дерево, доска, палка               |
| Добыча   | руда/камень         | камень, железная руда, уголь       |
| Охота    | животные            | еда, шкуры, мясо                   |
| Ремесло  | переработка         | верёвка, слиток, кожа, инструменты |
| Готовка  | еда из ингредиентов | хлеб, рагу, пирог                  |
| Торговля | рынок и банк        | золото, кредиты, проценты          |
| Бой      | монстры             | дроп, опыт, репутация              |
| Магия    | 3–5 заклинаний      | усиления, зелья, пассивные баффы   |

Гейт каждого скилла: уровень + рецепт/реквизит + зона (для боя).

### 2.2 Слои прогрессии

1. **Ресурсы → инструменты.** Топор и кирка ускоряют добычу; дальше — коварня,
   алхим-лаборатория.
2. **Скиллы и рецепты.** XP по кривой `xpNext = 15·level^1.4`; каждый уровень
   открывает рецепты и даёт +1 к максимальному множителю скилла.
3. **Бой.** 8 зон, у каждой монстры со `hp`, `damage`, `attackInterval`, `xp`,
   `dropTable`. Стамина тратится на удары, еда её восстанавливает.
4. **Экономика.** Рынок с дрейфом цен (seeded RNG, отдельный seed в состоянии),
   лавка (скидка на продажу / наценка на закупку), банк (депозит под процент,
   кредит под процент), аукцион (скупаем сломанное дёшево, перепродаём дорого).
5. **Постройки (апгрейды).** 12 штук: топор, кирка, кузница, костёр, лесорубка,
   каменоломня, ферма, алхим-лаборатория, банк, аукцион, телепорт, палатка. У
   каждой N уровней, цена `base·growth^level`, эффект — множитель производства
   или пассивный доход.
6. **Квесты.** 10 цепочек, разблокируют зоны, рецепты, бонусы. Награда —
   предметы/уровни скиллов/апгрейд.
7. **Prestige «Новый поход».** Сброс ресурсов, уровней, построек → Очки рассвета
   (множители золота, +стартовый уровень). Разные слои престижа по кривой
   Antimatter Dimensions.
8. **Временные события.** 5–6 штук (картофельный урожай, ярмарка, налёт волков):
   множители на 5–15 минут, шанс выпадения при тике.

### 2.3 Оффлайн-прогресс

Активное действие продолжается до конца (кап 12 ч), пассивные постройки копят
золото. Прогресс считается лениво: любой вызов MCP сначала «догоняет» тики до
текущего времени. Тик — чистая функция `tick(state, now) → state`.

## 3. Контент: стратегия B

### 3.1 Что откуда берём

| Источник                                                            | Что берём                                                                                                      | Ограничение                                                                    |
| ------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| Antimatter Dimensions (`IvarK/AntimatterDimensionsSourceCode`, MIT) | **структура** слоёв прогрессии: лестница измерений, уровни апгрейдов, многослойный престиж, формулы множителей | не копируем код и тексты; при прямом заимствовании — атрибуция MIT в README    |
| Melvor Idle (вики, числовые ориентиры)                              | **числовые ориентиры** кривых: порядок величин стоимости, скорости роста, времени окупаемости                  | числа — ориентир, не копия таблиц; в README указываем «по мотивам Melvor Idle» |
| Kittens Game, Bitburner                                             | ничего                                                                                                         | лицензии запрещают (WET PAWS / Commons Clause)                                 |

### 3.2 Формат контента

Все данные — в JSON, валидируются zod-схемами при старте:

```sh
content/
  skills.json      # id, name, description, xpCurve, unlockLevel, icon
  items.json       # id, name, type(resource|material|food|tool|quest), sellPrice, buyPrice
  recipes.json     # id, output, inputs[{item, qty}], skill, skillLevel, timeSec
  upgrades.json    # id, name, maxLevel, costBase, costGrowth, effect{kind, valuePerLevel}
  monsters.json    # id, name, zone, hp, damage, attackInterval, xp, dropTable[]
  zones.json       # id, name, unlock{quest|skillLevel}, monsters[]
  quests.json      # id, name, steps[{kind, target, qty}], rewards[]
  events.json      # id, name, durationSec, modifiers[], weight
  balance.json     # параметры кривых (генерируется автотюном)
```

Валидатор контента прогоняется при старте сервера: битый контент → сервер не
поднимается, падает с понятным сообщением (путь, id, что не так).

### 3.3 Баланс

Все числа выражены формулами, а не «на глаз»:

- цена апгрейда: `cost(level) = costBase · costGrowth^level`
- скорость производства:
  `rate = rateBase · (1 + k·skillLevel) · upgradeMult · prestigeMult`
  - `k` — коэффициент влияния уровня скилла, по умолчанию `k = 0.1`; значение
    хранится в `content/balance.json` (ключ `skillRateK`), чтобы автотюн крутил
    его без правок кода и рецептов
- XP: `xpToNext = 15 · level^1.4`
- скидка торговли: `min(0.4, 0.02·tradingLevel)`
- цена рынка: базовая ± 30%, дрейф каждые 5 минут, seeded RNG

Проверка баланса — симулятором (чистый домен, переиспользуется автотюном и
дебаг-страницей):

- прогон 1 / 6 / 24 / 72 часов;
- метрики: время до престижа, золото/мин по этапам, доля простоя, сколько узких
  мест (апгрейд дороже, чем окупается за 30 минут);
- критерий: каждый апгрейд окупается за 3–15 минут, престиж — за 2–6 часов,
  idling не превышает 60% времени.

## 4. MCP API

HTTP-эндпоинт: `POST/GET /mcp` (Streamable HTTP, `mcp-handler`). На том же
сервере: `/` (дебаг-страница), `/api/state` (JSON-снапшот для дебага).

### 4.1 Инструменты (13)

| Инструмент      | Назначение                                                                                |
| --------------- | ----------------------------------------------------------------------------------------- |
| `game_state`    | полный снейпшот: кошелёк, инвентарь, скиллы, активное действие, апгрейды, престиж, квесты |
| `game_action`   | старт / отмена / статус активного действия                                                |
| `game_craft`    | крафт: проверка ресурсов, уровня скилла, рецепта                                          |
| `game_upgrades` | список апгрейдов с ценами и эффектами / покупка уровня                                    |
| `game_trade`    | продажа / покупка по текущей рыночной цене                                                |
| `game_bank`     | депозит / вывод / кредит, ставки                                                          |
| `game_combat`   | карта зон и монстров / начать бой / отчёт и дроп                                          |
| `game_quests`   | прогресс квестов / клейм награды                                                          |
| `game_market`   | текущие цены, история, тренд                                                              |
| `game_skills`   | уровни, XP, доступные рецепты, цели следующего уровня                                     |
| `game_prestige` | предпросмотр (сколько даст очков) / запуск нового захода                                  |
| `game_log`      | лента событий: что куплено, что сломано, что заблокировано                                |
| `game_tick`     | форсировать продвижение времени (тесты, детерминизм, симуляции)                           |

Ограничения `game_tick` (иначе агент ломает баланс и оффлайн-кап):

- максимальный шаг за вызов — `maxTickSec` из `balance.json` (по умолчанию 3600
  с);
- суммарный форсированный сдвиг за игровые сутки — не больше `maxTickPerDaySec`
  (по умолчанию 24 ч);
- в dev-режиме (`NODE_ENV !== "production"`) ограничения сняты — там инструмент
  нужен симулятору и тестам;
- форсированные тики помечаются в ленте событий, чтобы их можно было отличить от
  реального времени.

### 4.2 Ресурсы и промпты

- Ресурсы: `game://state`, `game://skills`, `game://market`, `game://quests`.
- Промпт `game_strategy`: как эффективно играть (что покупать в каком порядке,
  как считать окупаемость, когда престижить) — чтобы любой MCP-клиент сразу
  получил релевантную стратегию.

### 4.3 Ошибки

Все мутации возвращают `Result` с доменной ошибкой, а не бросают исключение:
агент читает текст ошибки и чинит поведение. `game_log` дублирует ошибки в
ленту, чтобы агент мог разобрать историю.

`Result` — из `neverthrow` (`ok`/`err`, `Result<T, E>`). Доменная ошибка —
discriminated union `DomainError` с полем `code`, `message` и контекстом; текст
`message` агент получает в ответе инструмента как есть.

## 5. Дебаг-страница (human UI)

Статическая страница на том же HTTP-сервере, пишется руками (шаблон + немного JS
на клиенте), без генеративного UI:

- `/` — обзор: кошелёк, ключевые множители, активное действие с прогрессом и
  таймером, апгрейды с ценами и кнопкой «купить», скиллы с XP до следующего
  уровня, рынок, квесты, лента событий.
- Автообновление раз в 2 секунды (fetch `/api/state`), кнопка «пауза/продолжить»
  и «advance time» (через `game_tick`).
- Страница — только наблюдатель и ручной пульт: она не меняет правила игры, все
  действия идут через те же use cases, что и MCP-инструменты.
- `/api/state` — тот же снапшот, что отдаёт `game_state`.
- Доступ — по API-ключу (заголовок `X-API-Key` или `?key=` в dev-режиме);
  страница показывает, чей это игрок. В MVP ключ один, в R1 — по одному на
  игрока.

Разделение «наблюдение» и «мутации» (чтобы дебаг-страница не стала скрытым
админом):

- чтение (`/api/state`) — доступно по любому валидному ключу игрока;
- мутации с кнопок страницы («купить», «advance time», «пауза») — только по
  ключу с правом `play`; read-only ключ в R2 получает страницу без кнопок;
- в MVP один ключ = полный доступ, но код страницы всё равно разделяет read-only
  и mutating-части и не прячет «play» в разметке;
- `/api/state` без ключа в dev-режиме отдаёт дефолтного игрока — это явно
  помечено в UI бейджем «dev: default player», чтобы нельзя было спутать с
  доступом по ключу.

## 6. Архитектура

```sh
src/
  domain/            # чистое: нет I/O, нет таймеров, нет импортов Node-API
    game/            # state, actions, combat, market, bank, prestige, quests, events
    shared/          # Result, доменные ошибки, seeded RNG (mulberry32), кривые
  application/       # сценарии (use cases) + порты
    ports/           # GameRepository, Clock, Rng, ContentRepository,
                     # PlayerRepository, ApiKeyRepository
    use-cases/       # tick, start-action, cancel-action, craft, buy-upgrade,
                     # sell, buy, bank-op, start-fight, quest-progress, claim,
                     # prestige, get-state, simulate
  infrastructure/
    persistence/     # node:sqlite: players, api_keys, state(json), events, snapshots
    content/         # загрузка JSON + zod-валидация контента
    identity/        # выдача/проверка API-ключей, хэширование, resolve игрока
    mcp/             # сборка McpServer: tools/resources/prompts → use cases
    http/            # node:http сервер: /mcp (mcp-handler), /, /api/state,
                     # middleware: API-ключ → playerId
    sim/             # симулятор прогрессии + автотюн кривых
  bootstrap/
    server.ts        # composition root + HTTP сервер
    autotune.ts      # CLI: подбор параметров кривых → content/balance.json
    keys.ts          # CLI: выдача/отзыв API-ключей
tests/               # node:test: домен, use cases, контент-валидатор, e2e
```

Инварианты:

- `domain` и `application` не знают про MCP, HTTP, SQLite и таймеры.
- `tick(state, now)` — чистая функция; вся мутабельность — новая версия
  состояния.
- Время и случайность — через порты `Clock` и `Rng` (в состоянии хранится seed,
  поэтому тик детерминирован).
- Запись состояния — одной транзакцией; перед каждой записью — снапшот для
  отката.
- **Всё состояние игрока адресуется `playerId`**: репозитории принимают
  `playerId` параметром, состояние одного игрока никогда не видно другому.
- Идентификация — только по API-ключу (SHA-256 хэш в БД, исходный ключ
  показывается один раз при выдаче).

ориентиры Melvor по числам, а не готовые таблицы.

Критерий выхода из этапа: код этапа собирается (`npm run build`), тесты зелёные
(`npm test`), и этап можно взять в работу независимо от следующих.

## 8. Критерии готовности MVP

- `npm start` поднимает HTTP-сервер: `/mcp` отвечает по MCP, `/` показывает
  состояние.
- При первом старте сервер создаёт дефолтного игрока и печатает API-ключ один
  раз; запрос к `/mcp` без ключа (или с неверным) отклоняется с 401.
- Любой MCP-клиент (Claude Desktop, OpenCode, свой скрипт) подключается по HTTP
  с заголовком `Authorization: Bearer <key>` и видит 13 инструментов.
- Агент может за 10 минут пройти путь: добыча → крафт → продажа → апгрейд →
  уровень скилла → бой → квест → престиж.
- Стейт переживает перезапуск сервера, оффлайн-кап 12 ч корректно начисляется.
- Симулятор показывает: апгрейд окупается за 3–15 минут, престиж — за 2–6 часов.
- Два ключа одного игрока видят один и тот же стейт; ключ другого игрока —
  другой стейт (тест на изоляцию).
- Юнит-тесты на домен и use cases зелёные; `npm test` без сети и без БД работает
  (in-memory/SQLite `:memory:`).

## 9. Риски

| Риск                             | Решение                                                                                      |
| -------------------------------- | -------------------------------------------------------------------------------------------- |
| LLM вызывает невалидные действия | домен валидирует всё, ошибки возвращаются текстом, `game_log` для разбора                    |
| Поломанный баланс                | симулятор + автотюн, кривые в данных — крутятся без правок кода                              |
| Рассинхрон времени/гонки         | ленивый тик, версионирование состояния, транзакции и снапшоты                                |
| Рост `state`                     | компактизация ленты событий (cap N), снапшоты с TTL                                          |
| Лицензии                         | не копируем Kittens/Bitburner/Melvor; AD (MIT) — только референс, атрибуция в README         |
| Плагин/эксплойт в HTTP           | биндинг только на localhost, валидация входа, проверка ключа на каждом запросе               |
| Утечка API-ключа                 | в БД только SHA-256 хэш + префикс, исходный ключ показывается один раз; ключи можно отозвать |
| Ошибка изоляции игроков          | player-scoped репозитории, тест «два игрока — два разных стейта» в CI                        |

## 10. После MVP (вне объёма MVP)

### 10.1 Generative UI — новая постановка

Гипотеза «ИИ присылает целый HTML» отложена. Новая гипотеза: **ИИ присылает
отдельные куски** — CSS-переменные/токены и HTML-шаблоны для отдельных кастомных
элементов (виджетов), а страница собирается из них.

Ограничения, которые надо зафиксировать до реализации:

- агент отдаёт **фрагменты**, а не документ; страница собирается шаблоном;
- переиспользуемый контракт виджета: имя, данные (JSON-путь в снапшоте), слоты,
  css-токены;
- санитайзер фрагментов (whitelist тегов/атрибутов, `script`/`on*` вырезаются);
- изоляция: `iframe sandbox="allow-scripts"` без `allow-same-origin`;
- версионирование виджетов и сравнение версий между моделями.

Решить до начала: формат контракта (JSON Schema виджета), способ доставки
обновлений (poll / SSE), кто отвечает за общий визуальный язык (дизайн-токены в
`tokens.css`).

### 10.2 Прочее на потом

- Встроенный LLM-раннер (цикл observe → decide → act) с адаптерами
  OpenAI-compatible и Anthropic.
- ВебMCP-мост (`experimental_webMcp` в `mcp-handler`) — чтобы страницу могли
  читать агенты в браузере.
- Авторизация и удалённый доступ вместо localhost — см. §11 (фаза R2).
- Мультиплеер/соревнование моделей, метрики эффективности агента, запись решений
  в JSONL.

## 11. Roadmap: мультиплеер, API-ключи, авторизация

MVP обслуживает одного игрока, но схема БД и все репозитории **player-scoped с
первого дня**, поэтому фазы ниже — расширение, а не переделка.

### 11.1 Схема данных (player-scoped, с MVP)

```sql
players(
  id TEXT PRIMARY KEY,          -- uuid
  label TEXT NOT NULL,          -- "player-1", "мой-агент"
  created_at INTEGER NOT NULL,
  last_seen_at INTEGER,
  meta TEXT                     -- json: настройки, лимиты
)

api_keys(
  id TEXT PRIMARY KEY,
  player_id TEXT NOT NULL REFERENCES players(id),
  key_hash TEXT NOT NULL,       -- sha256 hex, уникальный индекс
  key_prefix TEXT NOT NULL,     -- "mcp_live_a1b2" — для отображения и поиска
  label TEXT,                   -- "ноутбук", "claude", "opencode"
  created_at INTEGER NOT NULL,
  last_used_at INTEGER,
  revoked_at INTEGER,
  scopes TEXT                   -- json: [] — задел под R2
)

game_states(
  player_id TEXT PRIMARY KEY REFERENCES players(id),
  state TEXT NOT NULL,          -- json GameState
  version INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
)

events(player_id, ts, type, payload)   -- лента игрока
snapshots(player_id, ts, state)        -- откат
```

### 11.2 Фаза R0 — MVP: один игрок, ключ есть уже сейчас

- При первом старте сервер создаёт дефолтного игрока, генерирует ключ и печатает
  его в консоль один раз.
- Формат ключа: `mcp_live_<base62, 32 символа>`; в БД — только `sha256(key)` +
  префикс.
- Передача ключа: `Authorization: Bearer <key>`; фолбэк — заголовок `X-API-Key`;
  query-параметр `?key=` только в dev-режисе (localhost) из-за утечки в логах.
- Middleware: каждый запрос `/mcp` и `/api/state` → resolve ключ → `playerId` →
  per-request `McpServer`, собранный на этого игрока. Реализация:
  `createMcpHandler(factory)`, фабрика получает `ctx.requestInfo` (сырой
  `Request`) и достаёт заголовок; `ctx.authInfo` — pass-through, если позже
  включим OAuth.
- Дебаг-страница принимает ключ (заголовок или `?key=`), показывает игрока и его
  состояние; без ключа в dev-режиме — дефолтный игрок.

### 11.3 Фаза R1 — мультиплеер (следующая после MVP)

- Выдача ключей: CLI `npm run keys:create -- --label "мой агент"`, локальный
  админ-эндпоинт `POST /admin/keys` (только localhost), позже — веб-страница
  управления ключами.
- Список и отзыв ключей: `npm run keys:list`, `npm run keys:revoke <id>`; отзыв
  = `revoked_at`, ключ перестаёт работать сразу.
- Изоляция: у каждого игрока свой `GameState`, свой seed RNG, своя лента событий
  и свои снапшоты; кэши игроков — по `playerId`.
- Ограничения (настраиваемые на игрока): rate limit запросов, максимум активных
  действий, кап уровней скилла (антифлуд), лимит оффлайн-капа.
- Наблюдение: `/admin/players` — список игроков, их золото, уровни, апгрейды,
  последняя активность; без вмешательства в их игру.
- Логи и метрики с `playerId`: кто какие инструменты вызывал, сколько ошибок,
  сколько действий в игре.

### 11.4 Фаза R2 — авторизация поверх API-ключей

Ключи остаются «рулеткой» для машин, а humans/аккаунты получают полноценный
вход:

- OAuth 2.1 по MCP-спецификации: в SDK есть готовые `requireBearerAuth`,
  `verifyBearerToken`, `bearerAuthChallengeResponse`,
  `buildOAuthProtectedResourceMetadata` — используем их вместо самописной
  проверки.
- Аккаунт → игроки: один аккаунт может владеть несколькими игроками (каждый —
  своя игра), ключи привязаны к игроку и/или аккаунту.
- Роли и scopes: `read` (только `game_state`, `game_skills`, `game_log`) и
  `play` (все мутации); read-only ключ — для наблюдателя/мониторинга.
- Сессии и отзыв: refresh-токены, отзыв всех ключей аккаунта, аудит-лог
  действий.
- Перенос на внешний хостинг: TLS-терминация, CORS, рейт-лимиты по IP и по
  аккаунту.

### 11.5 Порядок работ

| Фаза | Содержание                                                                  | Оценка     |
| ---- | --------------------------------------------------------------------------- | ---------- |
| R0   | player-scoped схема, дефолтный игрок, выдача ключа, middleware ключа        | +1 ч к MVP |
| R1   | CLI/админ выдача и отзыв ключей, изоляция игроков, лимиты, `/admin/players` | 3–4 дня    |
| R2   | OAuth 2.1, аккаунты, scopes, аудит, внешний хостинг                         | 4–6 дней   |
